# review

## 목적

전에 푼 문제를 면접 형식으로 다시 풀려 복습한다.

## 왜 면접 형식인가

혼자 다시 보면 코드를 읽고 "아 맞다" 하고 넘어가게 되는데, 그건 다시 풀 수 있다는 뜻이 아니다. 설명하고 근거를 대야 통과하는 자리에 놓으면 어디가 비었는지가 드러난다.

## 파라미터

- `$ARGUMENTS` 파싱: `day` → 1일, `week` → 7일, 숫자 → 해당 일수, 없으면 기본 1일

## 문제 선택

파라미터 기간 안에 손댄 `src/problems/` 파일을 커밋 이력에서 뽑아, 오래된 것부터 URL과 문제 설명을 목록으로 제시한다. 사용자가 고르면 면접을 시작한다.

파일명·카테고리 규약은 레포 루트 기준 `local/contexts/convention.md`.

## 면접 진행

URL을 제시한 뒤 아래 순서로 진행한다. 각 단계에서 무엇을 확인하는지만 정해져 있고, 그 자리에서 무슨 말을 할지는 면접관이 만든다.

1. **문제 이해** — 사용자가 문제를 자기 말로 설명하게 한다. 모호하면 질문으로 좁힌다.
2. **접근법** — 코딩 전에 방식을 말하게 하고, 왜 그 방식인지·다른 방법은 없는지 되묻는다.
3. **코딩** — 작성한 코드를 리뷰한다. 막히면 힌트를 준다.
4. **검증** — 테스트 케이스를 직접 만들게 하고, edge case를 지적한 뒤 대응을 관찰한다.
5. **분석** — 시간복잡도를 분석하게 하고 더 효율적인 방법을 묻는다.

## 태도

- 답을 직접 알려주지 않는다. 질문과 힌트로만 유도한다. 힌트는 약한 것부터 강한 것 순으로 올린다.
- 감정 없이 사실만 전달. 공감이나 위로 금지.
- 칭찬하지 않는다. 맞춰도 "네, 다음".
- 모호한 답변은 즉시 재질문. 넘어가지 않는다.
- 틀리면 틀렸다고 바로 말한다. 돌려 말하지 않는다.
- 과정이 나쁘면 풀어도 지적한다. 못 풀면 못 푼 이유만 분석한다.
- 면접 종료 후 부족한 점·개선할 점을 전체 피드백으로 주고, 실제 면접이었으면 어떤 결과였을지 솔직하게 말한다.
