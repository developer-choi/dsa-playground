# Adjacency Matrix vs Adjacency List

그래프를 코드로 옮기는 방법은 두 가지다: **인접 행렬**과 **인접 리스트**.
노드·간선·V·E 같은 말과 그래프 종류는 [graph.md](./graph.md).

아래 예시는 [graph.md](./graph.md)의 「예시로 확인하기」 그래프에 번호를 붙여 쓴다 — 제니 0, 딩코 1, 로제 2, 사나 3.
간선은 0-1(제니-딩코), 0-2(제니-로제), 2-3(로제-사나). V = 4, E = 3.

## 인접 행렬 (Adjacency Matrix)

2차원 배열로 표현한다. `graph[a][b]` 는 "a와 b가 연결되었는가".

```
   0  1  2  3
0  X  O  O  X
1  O  X  X  X
2  O  X  X  O
3  X  X  O  X
```

```js
const graph = [
  [false, true,  true,  false],
  [true,  false, false, false],
  [true,  false, false, true ],
  [false, false, true,  false],
];

graph[0][2]; // true — 연결 확인 O(1)
```

무방향이면 대각선을 기준으로 대칭이다 (`graph[a][b] === graph[b][a]`).
그래서 간선을 넣을 때 `graph[a][b]` 와 `graph[b][a]` 를 둘 다 채워야 한다.

- 연결 확인: **O(1)**
- 공간: **O(V²)** — 연결 안 된 조합까지 전부 칸을 차지한다

## 인접 리스트 (Adjacency List)

각 노드마다 "그 노드에 연결된 노드들"만 나열한다.

```
0 -> 1 -> 2
1 -> 0
2 -> 0 -> 3
3 -> 2
```

```js
// 노드가 0..N-1 번호면 배열
const graph = [
  [1, 2],
  [0],
  [0, 3],
  [2],
];

// 노드 이름이 번호가 아니면 객체(Map)
const graph = {
  제니: ['딩코', '로제'],
  딩코: ['제니'],
  로제: ['제니', '사나'],
  사나: ['로제'],
};

graph[0].includes(2); // true — 0의 이웃을 훑어야 한다
```

- 연결 확인: **O(해당 노드의 이웃 수)** — 최악 O(V)
- 공간: **O(V + E)** — 실제 있는 간선만 저장한다

## 둘의 차이 = 시간 vs 공간

| | 연결 확인 | 공간 |
|---|---|---|
| 인접 행렬 | O(1) | O(V²) |
| 인접 리스트 | O(이웃 수), 최악 O(V) | O(V + E) |

행렬은 "0과 2가 연결됐나?"를 즉시 답하는 대신, 연결 안 된 조합까지 전부 저장한다.
리스트는 저장을 아끼는 대신, 연결 여부를 알려면 그 노드의 이웃을 훑어야 한다.

한편 **"한 노드의 이웃을 전부 순회"** 는 리스트가 O(이웃 수), 행렬이 O(V)로 리스트가 유리하다.
DFS/BFS는 이 순회를 반복하는 작업이라 보통 인접 리스트를 쓴다.

## 인접 리스트로 방향 나타내기

인접 리스트는 무방향·단방향을 **둘 다** 표현한다. 자료 구조가 다른 게 아니라, 양쪽에 다 적느냐 한쪽만 적느냐가 다르다.

`graph[a]` 는 "a에서 **갈 수 있는** 곳들"이다. 화살표 목록이라고 보면 된다.

```js
// 단방향 — 1에서 2로만 갈 수 있다
{
  1: [2],
  2: [],
}

// 무방향 — 1과 2가 서로 오갈 수 있다
{
  1: [2],
  2: [1],   // 양쪽에 다 적는다
}
```

무방향이라고 해서 별도 표기가 있는 게 아니라, **왕복 화살표 두 개로 적는 것**이 무방향이다.

주의할 점은 **코드만 보고는 무방향인지 단방향인지 알 수 없다**는 것이다.
위 두 예시는 문법적으로 같은 모양이고, 양쪽에 다 적혀 있으면 "무방향으로 쓴 것"이라고 읽을 뿐이다.

그래서 **인접 리스트를 만드는 그 순간에** 양쪽에 넣을지 한쪽만 넣을지를 의식적으로 정해야 한다.
이 선택이 순회 코드의 모양을 결정한다 ([dfs.md](./dfs.md)의 「원인은 인접 리스트를 만들 때 이미 정해진다」).

### 어느 쪽으로 만들지는 입력이 알려준다

**입력이 방향을 이미 말해주고 있으면 그대로 한쪽만 적는다.**
`[상위, 하위]`, `[부모, 자식]`, `[선수과목, 후속과목]` 처럼 두 자리의 뜻이 서로 다르면 그게 방향이다.
`[a, b]` 로 두 자리가 대등하게 주어지면 무방향이므로 양쪽에 적을 수밖에 없다.

위로 올라갈 길이 생기니 되돌아가는 걸 막을 `visited` 가 필요해지고, 원래 방향을 되찾으려고
부모 명단 같은 자료구조를 따로 들게 된다.

[wf-4 디렉토리 경로](../../src/problems/tree/wf-4.ts)가 그 사례다. `relation` 이 `[상위, 하위]` 로
방향을 주는데 양쪽에 다 적었다가 `visited` 와 부모 명단이 딸려 왔고, 부모 명단을 노드마다 복사하느라
O(N²) 로 무너졌다.

```ts
// ❌ 입력이 준 방향을 버리고 양쪽에 다 적음
for (const [parent, child] of relation) {
  graph[parent].push(child);
  graph[child].push(parent);   // ← 이 한 줄이 아래 둘을 불러온다
}
const visited = new Set([1]);  // 위로 되돌아갈 수 있으니 막아야 한다
const parents = {};            // 방향을 잃었으니 따로 들고 다녀야 한다

// ✅ 입력에 적힌 방향 그대로 한쪽만
for (const [parent, child] of relation) {
  graph[parent].push(child);
}
// visited 도 parents 도 없다 — 위로 갈 길 자체가 없다
```

들고 다니는 자료구조가 셋에서 하나로 줄었다. `visited` 를 뺀 게 최적화라서가 아니라,
**뺄 수 있는 상태로 만들고 시작했기 때문**이다.
